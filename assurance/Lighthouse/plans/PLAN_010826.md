# SafetyNet Landing-Page Remediation Plan

## Summary

- Target current GitHub `main`, which matches the supplied Lighthouse reports. The local checkout is stale on `codex-fix-hero-layout-and-modal-buttons`; its untracked `landingpage_structure_chat_130526.md` will be preserved.
- The site is static HTML, Tailwind CSS 4, vanilla ES modules, and static images. `vercel.json` supplies hosting headers; production is Cloudflare-proxied. There is no automated image pipeline.
- The mobile LCP element is the hero H1, not the hero image. Lighthouse reports simulated LCP of 7.565 seconds, while its observed H1 breakdown is about 223 ms TTFB plus 380 ms render delay. The exact simulation gap is not fully attributable without the raw trace.
- The dominant first-party opportunities are the eagerly downloaded 890,547-byte founder image, responsive hero delivery, Google Fonts/render-path dependencies, and contrast failures. TBT is already healthy; broad JavaScript removal is not justified.
- Phase 2 will make local changes only. No commit, push, PR, preview deployment, production deployment, Cloudflare setting change, or real signup submission is authorized.

## Risks, Assumptions, and Boundaries

- Self-hosting the exact Inter face is chosen to minimize text wrapping changes. The font file and license will be sourced from the current audited face/official Inter distribution.
- The remote default branch is authoritative. The local May branch and stale local `origin/main` will not be edited.
- The mobile LCP simulation gap is not conclusively explained by the JSON alone. Post-change traces must confirm whether founder-image contention, webfont repaint, or another scheduling effect dominates.
- Darker teal is an intentional visual adjustment required for AA contrast. Image-dependent white nav text will receive a deterministic opaque backdrop rather than relying on variable photograph pixels.
- The repository has no first-party TikTok pixel or campaign-attribution submission logic. Existing query strings and Cloudflare RUM behavior will be preserved; no new tracking will be added.
- `vercel.json` indicates a Vercel-oriented configuration, but the production edge behavior is Cloudflare-controlled. The actual deployment pipeline/account configuration is not verifiable from the repository alone.
- Cloudflare managed challenge deprecations, third-party cookies, Insights caching, and email-obfuscation resources cannot be fixed in this repository. They will remain reported rather than suppressed.
- The Worker implementation, Supabase database/RLS, email delivery, privacy compliance, dependency security audit, and production abuse controls are outside this repository and outside this remediation.
- Local Lighthouse omits the production Cloudflare edge layer and cannot establish deployed paid-traffic readiness. Without a separately authorized preview/production deployment and live functional test, the maximum defensible final outcome is `CONDITIONAL PASS`.
- Temporary external downloads in Phase 2: npm packages from the existing lockfile, the approved Axe development tool, Playwright Chromium if not cached, Inter/font license files, and pinned Lighthouse CLI. These are reversible; no external repository or production state changes.
- A real production signup would write through the Cloudflare Worker to backend storage and may send email. It will not be attempted without separate approval and a designated test address.
